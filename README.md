# Персонотека — биографический портал (personoteka.ru)

Реализация ТЗ «биографический портал „Персонотека“», версия 1.0.
Ссылки вида «§7.2» в комментариях к коду указывают на разделы ТЗ.

## Стек

- **Next.js 16 (App Router) + TypeScript**, рендеринг SSG: страницы персон и рубрик
  собираются статически, витрины с датой (`/`, `/rejting/`, `/rodilis-segodnya/`)
  ревалидируются раз в час.
- **CSS Modules + токены дизайн-системы** (`src/styles/tokens.css`). Utility-фреймворка
  поверх дизайн-системы нет — сознательно (§9.1).
- **Шрифты** Literata / Inter / JetBrains Mono — self-hosted `woff2`, подмножества
  latin + cyrillic, `font-display: swap`. Внешние CDN не используются (§7.3).
- **Контент** — файлы в `content/`. Слой доступа изолирован в `src/lib/content.ts`:
  при переезде на headless CMS меняется только он, страницы не трогаем.
- **PDF-досье** — `@react-pdf/renderer` с теми же шрифтами, что на сайте (§6.3).
- **OG-картинки** — `next/og`, генерация на лету (§10.1).

## Команды

```bash
npm install
npm run dev              # localhost:3000 (соберёт индекс поиска и запустит dev-сервер)
npm run build            # прод-сборка (prebuild сам пересоберёт индекс поиска)
npm start                # прод-сервер

npm run check            # содержимое + контрасты + типы, годится для CI
npm run check:content    # целостность контента: слаги, рубрики, тарифы, редиректы
npm run check:contrast   # WCAG-аудит палитры в обеих темах (критерий приёмки §15)
npm run rating           # пересчёт индекса внимания (§6.2)
npm run build:search     # пересборка public/search-index.json
npm run queue            # пересборка редакционной очереди из queue-roster.txt
npm run agentstvo        # учётная запись агентства (см. раздел «Кабинет»)
npm run photo            # приём портрета из локального файла (§7.5)
npm run photos:fetch     # скачивание портретов по content/photo-sources.json
```

## Что осознанно не сделано

- **Кабинет владельца профиля** — этап 6 дорожной карты (§15). Роли сейчас две:
  редакция (общий пароль) и агентство (своя учётная запись). Персональных
  учёток редакторов и кабинета героя нет; для них нужна полноценная база
  пользователей.
- **Внешняя аналитика.** В кабинете агентства показываются просмотры со
  своего счётчика (`src/lib/views.ts`) — по дням, без cookie и без опознания
  людей. Позиций в поиске, источников трафика и уникальных посетителей там нет
  и не появится без Метрики; в текстах кабинета это сказано прямо.
- **Headless CMS, PostgreSQL, Meilisearch** — источник контента пока файловый.
  Границы для замены обозначены в `src/lib/content.ts` и `src/lib/search.ts`.
- **CRM.** Заявки и запросы на удаление теперь пишутся в реестр
  (`src/lib/tickets.ts`, append-only JSONL) и видны в кабинете на
  `/lk/zayavki/` вместе со сроками §11.3 — это закрывает прежний долг по
  §11.3, а уведомления о новых обращениях уходят письмом (`src/lib/mail.ts`).
  Чего нет: выгрузки в CRM и статусов сделки.
  Каталог реестра задаётся переменной `DATA_DIR` и **обязан указывать на
  постоянный том** — иначе данные пропадут при пересборке контейнера, и
  кабинет об этом предупреждает прямо на странице.
- **Капча.** Код проверки Yandex SmartCaptcha готов; без переменной
  `SMARTCAPTCHA_SERVER_KEY` проверка пропускается, чтобы формы работали на стенде.
  На проде переменная обязательна.
- **Регистрация СМИ, уведомление РКН, оферта, реквизиты** — организационные шаги
  (§11.5, §15 этап 3). В текстах сайта нет обещаний «публикации в СМИ»,
  блок свидетельства в подвале появится, когда будет заполнен `SITE.smiCertificate`.
- **Правовые тексты** (`/politika-konfidencialnosti/`, `/pravila/`) — рабочая основа
  по структуре ТЗ, помечены как проект и требуют проверки юристом.

## Кабинет

`/lk/` закрыт middleware целиком. Ролей две, и их зоны не пересекаются.

**Редакция** входит по `LK_PASSWORD`: обзор наполнения, заявки и запросы со
сроками §11.3, материалы агентств с кнопкой снятия, очередь публикаций,
качество карточек.

**Агентство** входит по своему логину: свои страницы с просмотрами, лимит
подписки и форма публикации. Учётная запись заводится командой — регистрации
на сайте нет:

```
npm run agentstvo -- --name "Агентство Пример" --login primer --password '…'
npm run agentstvo -- --list
npm run agentstvo -- --login primer --password 'новый'   # сменить пароль
npm run agentstvo -- --login primer --disable            # приостановить
```

Команду нужно запускать с тем же `DATA_DIR`, что и приложение.

### Как устроена агентская публикация

Форма собирает карточку по шаблону портала и проверяет всё, что проверяется
машиной: объём, длину лида и подзаголовка, рубрики по справочнику, свободный
слаг, обязательные источники, согласие героя и сверку с реестром иноагентов.
Портрет обрезается под 4:5 тем же правилом, что и редакционный конвейер.

Страница пишется в `DATA_DIR/persons` и появляется на сайте сразу — так продан
тариф. Слой контента (`src/lib/content.ts`) читает оба источника; при совпадении
слага побеждает репозиторий, поэтому подменить редакционную страницу через
кабинет нельзя. После записи сбрасывается кэш всего сайта, иначе персона не
попала бы в каталог, рубрику и город. Поиск дополняется на лету
(`/api/poisk-index/`): статический индекс собирается на сборке и не знает о том,
что опубликовано после неё.

Проверка редакции — постфактум, на `/lk/agentskie/`. На самой странице стоит
оговорка о происхождении материала: читатель должен видеть, что текст написан
представителем героя, а не редакцией.

## Наполнение

Список персон к публикации живёт в `content/queue-roster.txt`, очередь собирается
командой `npm run queue`. Скрипт сам приводит ФИО к виду «Имя Фамилия», считает слаг
по §4.1, ловит совпадения и зарезервированные слова и проставляет статус
(`queued` / `drafting` / `published`) по фактическому наличию и статусу файла персоны.

**Публикуется только то, что подтверждено источниками.** По §5.3 каждое проверяемое
утверждение сопровождается ссылкой либо пометкой «со слов героя»; по §11.2 биография
третьего лица публикуется при согласии героя либо при статусе публичной фигуры и
общедоступности сведений. Поэтому персоны из очереди делятся на две группы:

- **публичные фигуры** — материал пишется по открытым источникам, список которых
  выводится на странице в блоке «Источники»;
- **все остальные** — сначала заявка, анкета и согласие (§12), только потом текст.
  До этого запись остаётся в очереди со статусом `queued`, а не превращается
  в правдоподобный, но непроверенный текст.

### Портреты

Два пути, подробности — в `design/photos/README.md`.

Автоматический: персона вписывается в `content/photo-sources.json` — для
публичной фигуры достаточно названия статьи в Википедии. Дальше цепочка
статья → элемент Викиданных → свойство P18 «изображение» → API Викисклада,
откуда берутся и файл, и автор, и лицензия. Запускает это workflow
«Портреты персон» (Actions → Run workflow) и коммитит результат в ту же
ветку: локально сеть закрыта.

Ручной: файл кладётся в `design/photos/`, дальше `npm run photo`.

Оба пути идут через один конвейер (`scripts/lib/portrait.ts`): кадр 4:5 по
лицу, 1200×1500, единая мягкая коррекция — иначе галерея снимков от разных
фотографов не выглядит одним каталогом. Лицензия обязательна в обоих; при
несвободной лицензии скрипт отказывается публиковать снимок.

## Дополнение к ТЗ: маркировка иностранных агентов

В §11 такого требования нет, но по 255-ФЗ материал о лице, включённом в реестр
иностранных агентов, обязан нести соответствующую пометку. В присланном списке персон
такие имена есть, поэтому в контент-модель добавлено поле `foreign_agent`
(дата сверки, факт включения, ссылка на запись реестра), а на странице персоны —
компонент `ForeignAgentNotice` с установленной законом формулировкой.

`npm run check:content` предупреждает о персонах без отметки о сверке и не пропускает
пометку без ссылки на реестр. Проставляет отметку только редакция, по актуальному
реестру Минюста: ошибочная пометка так же недопустима, как её отсутствие.

## Отступления от ТЗ

Три токена палитры затемнены относительно §7.2, потому что в исходных значениях
не выполнялся критерий приёмки §15 («контраст всех текстовых пар ≥ 4.5:1»):

| Токен | Было | Стало | Причина |
|---|---|---|---|
| `--ink-3` | `#6B7480` | `#666F7A` | 4.19:1 на `--surface-alt` (подвал, чередующиеся секции) |
| `--success` / `--verified` | `#2E7D57` | `#2D7C56` | 4.44:1 на `--surface-alt` |
| `--warning` | `#B4700E` | `#9C610C` | 3.82:1 на бумаге |

Все значения проверяются автотестом `npm run check:contrast`, который читает их
прямо из `tokens.css`.

Холодная часть палитры §7.2 развёрнута в шкалу `--cool-50 / 100 / 300 / 600`.
ТЗ отводит холодному роль «данных и служебных состояний», но одного текстового
оттенка для этого мало: нужны подложка секции, фон шапки таблицы и декоративная
линейка. Правило распределения — тёплое отвечает за «кто написал и что сделать»
(редакция, кнопки, активные пункты), холодное за «сколько и какое место»
(рейтинг, счётчики, фильтры, указатель). `--cool-100` темнее остальных подложек,
поэтому текстом на нём допустимы только `--ink`, `--ink-2` и `--cool-600` —
ограничение зафиксировано в `tokens.css` и проверяется автотестом.

К перечню тарифов §5.1 добавлено значение `editorial` — материал, подготовленный
редакцией по своей инициативе. Объёмы из §5.3 — это обязательства перед плательщиком,
и мерить ими редакционный материал неверно: у `editorial` свой коридор 1 200–12 000
знаков. Рекламы на таких страницах нет, как и на платных.

Индекс внимания не присваивается персонам без единого сигнала за 30 дней. Иначе на
старте, когда аналитика ещё не набрана, минимакс дал бы всем одинаковое число, и
витрина выдавала бы отсутствие статистики за результат. Пока сигналов нет,
`/rejting/` показывает пустое состояние с объяснением, а «Персона недели» на главной
берётся по дате публикации.

## Переменные окружения

```
NEXT_PUBLIC_SITE_URL=https://personoteka.ru   # по умолчанию именно это значение
SMARTCAPTCHA_SERVER_KEY=…                     # обязательна на проде (§9.4)
LK_PASSWORD=…                                 # пароль кабинета редакции
LK_SECRET=…                                   # ключ подписи сессии, необязателен
DATA_DIR=/data                                # данные, появившиеся после сборки
AGENCY_EDITOR=a-mejster                       # дежурный редактор агентских страниц
SMTP_HOST=smtp.yandex.ru                      # уведомления о заявках и запросах
SMTP_PORT=465                                 # 465 — SSL, 587 — STARTTLS
SMTP_USER=…                                   # ящик отправителя
SMTP_PASSWORD=…                               # пароль приложения, не пароль от почты
MAIL_FROM=…                                   # по умолчанию SMTP_USER
NOTIFY_EMAIL=dron939@yandex.ru                # куда падают уведомления
YANDEX_VERIFICATION=…                         # код из Яндекс.Вебмастера
GOOGLE_SITE_VERIFICATION=…                    # код из Google Search Console
INDEXNOW_KEY=…                                # 8–128 букв, цифр и дефисов
```

Почта уведомляет о новых заявках с лендинга и о запросах на удаление данных
(§11.3: ответственный узнаёт о запросе, а не находит его при следующем визите).
Письмо уходит **после** записи в реестр и на ответ формы не влияет: не
настроенная или упавшая почта не может стать причиной отказа человеку. Пока
`SMTP_HOST` не задан, отправка пропускается, а кабинет предупреждает об этом на
`/lk/zayavki/`. `NOTIFY_EMAIL` — внутренний адрес; читателям на сайте показан
редакционный `SITE.email`.

`DATA_DIR` — каталог на **постоянном** томе. Если переменная не задана, данные
пишутся в `/data` при его наличии, иначе в `.data` внутри проекта: последнее
годится для стенда и теряется при пересборке контейнера. Кабинет показывает
фактический путь и предупреждает, когда он непостоянный.

Внутри лежит всё, что появляется после сборки:

```
agentstva.json     учётные записи агентств (scrypt-хеши паролей)
persons/           страницы, опубликованные агентствами
media/             портреты, загруженные из кабинета
zayavki.jsonl      заявки с лендинга + журнал согласий
udalenie.jsonl     запросы на удаление + сроки §11.3
sobytiya.jsonl     смены состояния обращений
prosmotry.json     счётчик просмотров по дням
```

Здесь ПДн и журнал согласий — доступ нужен только приложению.
`AGENCY_EDITOR` — слаг редактора из `content/editors.json`, который отвечает за
постпроверку агентских материалов; без переменной берётся первый в списке.

Без `LK_PASSWORD` раздел `/lk/` выключен целиком и показывает только страницу
входа с объяснением. Это сделано намеренно: кабинет отдаёт редакционную очередь,
где есть имена людей, ещё не давших согласия на публикацию, и неподготовленный
деплой не должен открывать их по умолчанию.

`NEXT_PUBLIC_SITE_URL` подставляется в канонические адреса, карты сайта, JSON-LD
и OG-картинки. На тестовом стенде его нужно выставить в фактический адрес стенда,
иначе разметка будет ссылаться на боевой домен.

## Индексация

Разметка и карты сайта отдаются всегда, без настройки. Три переменные включают
то, что без них работать не может.

`YANDEX_VERIFICATION` и `GOOGLE_SITE_VERIFICATION` — коды подтверждения прав
из Яндекс.Вебмастера и Google Search Console. Из способов подтверждения выбран
мета-тег, а не файл в корне: файл теряется при первом же переносе хостинга,
тег живёт в коде. Пока переменных нет, теги не выводятся — это нормально
до регистрации.

**Важно:** страницы пререндерятся на сборке, поэтому обе переменные читаются
на этапе `npm run build`, а не при запуске. Добавили код — нужна пересборка,
иначе тега в HTML не будет. Если сборщик не отдаёт переменные окружения,
подтверждение проще сделать записью TXT в DNS: и Яндекс, и Google этот способ
принимают, DNS-зона домена и так под рукой, а пересборка не нужна вовсе.
У Google подтверждение по DNS вдобавок даёт ресурс на весь домен, а не
на один протокол и хост.

`INDEXNOW_KEY` — произвольная строка из 8–128 латинских букв, цифр и дефисов.
Она отдаётся по адресу `/indexnow.txt` и позволяет просить Яндекс и Bing
о переобходе сразу, не дожидаясь планового. Ключ намеренно не лежит
в репозитории: с ним любой может слать заявки от имени домена. Google IndexNow
не поддерживает и ходит по карте сайта сам; ping карты через `/ping?sitemap=`
он отключил в 2023 году, поэтому его в проекте нет.

```
npm run indexnow                # всё: персоны, рубрики, города, разделы
npm run indexnow -- --since=7   # только изменённое за неделю
npm run indexnow -- --dry       # показать список и ничего не отправлять
```

Полный список уместен один раз, после первой выкладки. В расписании нужен
`--since`: заявки на неизменившиеся страницы поисковик считает шумом.
Страницы, опубликованные агентствами через кабинет, уходят в IndexNow сами —
сразу после записи и не задерживая ответ формы.

## Развёртывание на Amvera

Конфигурация — `amvera.yaml` в корне. Имя файла обязано быть именно таким:
вариант `amvera.yml` платформа не находит и молча уходит на настройки по
умолчанию — запускает `dev` вместо `start` и снимает контейнер по SIGTERM.

Значения для мастера настройки:

| Поле | Значение |
|---|---|
| Окружение | `node` |
| Инструмент | `npm` |
| Версия | `20` — Next 16 требует Node ≥ 20.9, ниже сборка упадёт |
| build → skip | **выключено**: без сборки не будет ни `node_modules`, ни `.next` |
| build → additionalCommands | `npm run build` |
| build → artifacts | пусто — приложению нужны и `.next`, и `node_modules`, и `content` |
| run → command | `npm run start` |
| run → containerPort | `3000` |

Что важно для этого проекта:

- **Порт и хост заданы жёстко:** `next start -H 0.0.0.0 -p 3000`. Документация
  Amvera называет ровно две причины ошибки 502/503 при статусе «приложение
  запущено»: приложение слушает не тот порт, что указан в `containerPort`,
  и хост оставлен `localhost` вместо `0.0.0.0`. Раньше порт брался из `$PORT` —
  значение, которое нельзя проверить заранее; при несовпадении платформа
  не достучится до приложения и снимет контейнер по SIGTERM. Обе величины
  теперь явные и совпадают с `containerPort`.
- **Инструменты сборки в `dependencies`.** `typescript`, `tsx` и `@types/*` лежат
  не в `devDependencies` намеренно: сборка идёт на сервере, и если окружение
  ставит зависимости с `NODE_ENV=production`, devDependencies были бы пропущены.
- **Индекс поиска** пересобирается сам: `prebuild` вызывает `build:search` перед
  `next build`.
- **Переменные окружения** задаются в панели Amvera; как минимум
  `NEXT_PUBLIC_SITE_URL` с фактическим адресом приложения.
- **Не статический хостинг.** Приложению нужен Node-процесс: страницы персон
  статические, но `/katalog/` рендерится по фильтрам из строки запроса,
  а формы и генерация PDF-досье живут в обработчиках маршрутов.
