# Персонотека — биографический портал (personoteka.ru)

Реализация ТЗ «биографический портал „Персонотека“», версия 1.0.
Ссылки вида «§7.2» в комментариях к коду указывают на разделы ТЗ.

## Стек

- **Next.js 16 (App Router) + TypeScript**, рендеринг SSG: страницы персон и рубрик
  собираются статически, витрины с датой (`/`, `/rejting/`, `/rodilis-segodnya/`)
  ревалидируются раз в час.
- **CSS Modules + токены дизайн-системы** (`src/styles/tokens.css`). Utility-фреймворка
  поверх дизайн-системы нет — сознательно (§9.1).
- **Шрифты** Literata / Inter / JetBrains Mono — self-hosted `woff2`, подмножества
  latin + cyrillic, `font-display: swap`. Внешние CDN не используются (§7.3).
- **Контент** — файлы в `content/`. Слой доступа изолирован в `src/lib/content.ts`:
  при переезде на headless CMS меняется только он, страницы не трогаем.
- **PDF-досье** — `@react-pdf/renderer` с теми же шрифтами, что на сайте (§6.3).
- **OG-картинки** — `next/og`, генерация на лету (§10.1).

## Команды

```bash
npm install
npm run dev              # localhost:3000 (соберёт индекс поиска и запустит dev-сервер)
npm run build            # прод-сборка (prebuild сам пересоберёт индекс поиска)
npm start                # прод-сервер

npm run check            # содержимое + контрасты + типы, годится для CI
npm run check:content    # целостность контента: слаги, рубрики, тарифы, редиректы
npm run check:contrast   # WCAG-аудит палитры в обеих темах (критерий приёмки §15)
npm run rating           # пересчёт индекса внимания (§6.2)
npm run build:search     # пересборка public/search-index.json
npm run queue            # пересборка редакционной очереди из queue-roster.txt
```

## Структура

```
content/                 источник контента (будущая CMS)
  persons/*.json         персоны, одна на файл, имя файла = слаг
  articles/*.json        новости и интервью
  spheres.json           сферы деятельности
  cities.json            города
  editors.json           редакция (страницы авторов, E-E-A-T §10.3)
  metrics.json           сырые метрики для индекса внимания
  rating.json            снапшот рейтинга — результат пересчёта, не редактируется руками
  redirects.json         реестр 301 для изменённых слагов (§4.1)
  queue-roster.txt       список персон к публикации (правит редактор)
  queue.json             редакционная очередь — результат `npm run queue`

src/app/                 маршруты App Router
  [slug]/                СТРАНИЦА ПЕРСОНЫ — слаг в корне домена (§4.1)
  katalog/ sfera/ gorod/ rejting/ …   витрины и рубрики
  api/                   формы, PDF-досье
  sitemap*.xml/ robots.ts llms.txt/ feed.xml/   SEO-обвязка (§10)

src/components/          библиотека компонентов (§7.6)
src/lib/                 контент, поиск, рейтинг, разметка, согласия
src/styles/              токены, шрифты, глобальные стили
scripts/                 пересчёт рейтинга, сборка индекса, проверки
```

## Что осознанно не сделано

- **Личный кабинет и админка** — этап 6 дорожной карты (§15). `/lk/` показывает
  состав будущих разделов и не даёт ложного входа.
- **Headless CMS, PostgreSQL, Meilisearch** — источник контента пока файловый.
  Границы для замены обозначены в `src/lib/content.ts` и `src/lib/search.ts`.
- **Хранение заявок и тикетов.** Обработчики `/api/zayavka` и `/api/udalenie`
  валидируют данные и собирают записи журнала согласий, но пишут их в лог:
  подключение БД и CRM помечено `TODO(этап 4)`. **До запуска приёма заявок
  это обязательно к доделке** — иначе не выполняется §11.3.
- **Капча.** Код проверки Yandex SmartCaptcha готов; без переменной
  `SMARTCAPTCHA_SERVER_KEY` проверка пропускается, чтобы формы работали на стенде.
  На проде переменная обязательна.
- **Регистрация СМИ, уведомление РКН, оферта, реквизиты** — организационные шаги
  (§11.5, §15 этап 3). В текстах сайта нет обещаний «публикации в СМИ»,
  блок свидетельства в подвале появится, когда будет заполнен `SITE.smiCertificate`.
- **Правовые тексты** (`/politika-konfidencialnosti/`, `/pravila/`) — рабочая основа
  по структуре ТЗ, помечены как проект и требуют проверки юристом.

## Наполнение

Список персон к публикации живёт в `content/queue-roster.txt`, очередь собирается
командой `npm run queue`. Скрипт сам приводит ФИО к виду «Имя Фамилия», считает слаг
по §4.1, ловит совпадения и зарезервированные слова и проставляет статус
(`queued` / `drafting` / `published`) по фактическому наличию и статусу файла персоны.

**Публикуется только то, что подтверждено источниками.** По §5.3 каждое проверяемое
утверждение сопровождается ссылкой либо пометкой «со слов героя»; по §11.2 биография
третьего лица публикуется при согласии героя либо при статусе публичной фигуры и
общедоступности сведений. Поэтому персоны из очереди делятся на две группы:

- **публичные фигуры** — материал пишется по открытым источникам, список которых
  выводится на странице в блоке «Источники»;
- **все остальные** — сначала заявка, анкета и согласие (§12), только потом текст.
  До этого запись остаётся в очереди со статусом `queued`, а не превращается
  в правдоподобный, но непроверенный текст.

## Дополнение к ТЗ: маркировка иностранных агентов

В §11 такого требования нет, но по 255-ФЗ материал о лице, включённом в реестр
иностранных агентов, обязан нести соответствующую пометку. В присланном списке персон
такие имена есть, поэтому в контент-модель добавлено поле `foreign_agent`
(дата сверки, факт включения, ссылка на запись реестра), а на странице персоны —
компонент `ForeignAgentNotice` с установленной законом формулировкой.

`npm run check:content` предупреждает о персонах без отметки о сверке и не пропускает
пометку без ссылки на реестр. Проставляет отметку только редакция, по актуальному
реестру Минюста: ошибочная пометка так же недопустима, как её отсутствие.

## Отступления от ТЗ

Три токена палитры затемнены относительно §7.2, потому что в исходных значениях
не выполнялся критерий приёмки §15 («контраст всех текстовых пар ≥ 4.5:1»):

| Токен | Было | Стало | Причина |
|---|---|---|---|
| `--ink-3` | `#6B7480` | `#666F7A` | 4.19:1 на `--surface-alt` (подвал, чередующиеся секции) |
| `--success` / `--verified` | `#2E7D57` | `#2D7C56` | 4.44:1 на `--surface-alt` |
| `--warning` | `#B4700E` | `#9C610C` | 3.82:1 на бумаге |

Все значения проверяются автотестом `npm run check:contrast`, который читает их
прямо из `tokens.css`.

К перечню тарифов §5.1 добавлено значение `editorial` — материал, подготовленный
редакцией по своей инициативе. Объёмы из §5.3 — это обязательства перед плательщиком,
и мерить ими редакционный материал неверно: у `editorial` свой коридор 1 200–12 000
знаков. Рекламы на таких страницах нет, как и на платных.

Индекс внимания не присваивается персонам без единого сигнала за 30 дней. Иначе на
старте, когда аналитика ещё не набрана, минимакс дал бы всем одинаковое число, и
витрина выдавала бы отсутствие статистики за результат. Пока сигналов нет,
`/rejting/` показывает пустое состояние с объяснением, а «Персона недели» на главной
берётся по дате публикации.

## Переменные окружения

```
NEXT_PUBLIC_SITE_URL=https://personoteka.ru   # по умолчанию именно это значение
SMARTCAPTCHA_SERVER_KEY=…                     # обязательна на проде (§9.4)
```

`NEXT_PUBLIC_SITE_URL` подставляется в канонические адреса, карты сайта, JSON-LD
и OG-картинки. На тестовом стенде его нужно выставить в фактический адрес стенда,
иначе разметка будет ссылаться на боевой домен.

## Развёртывание на Amvera

Конфигурация — `amvera.yml` в корне. Значения для мастера настройки:

| Поле | Значение |
|---|---|
| Окружение | `node` |
| Инструмент | `npm` |
| Версия | `20` — Next 16 требует Node ≥ 20.9, ниже сборка упадёт |
| build → skip | **выключено**: без сборки не будет ни `node_modules`, ни `.next` |
| build → additionalCommands | `npm run build` |
| build → artifacts | пусто — приложению нужны и `.next`, и `node_modules`, и `content` |
| run → command | `npm run start` |
| run → containerPort | `3000` |

Что важно для этого проекта:

- **Порт.** Скрипт `start` читает `$PORT` и по умолчанию слушает 3000 — значение
  должно совпадать с `containerPort`.
- **Инструменты сборки в `dependencies`.** `typescript`, `tsx` и `@types/*` лежат
  не в `devDependencies` намеренно: сборка идёт на сервере, и если окружение
  ставит зависимости с `NODE_ENV=production`, devDependencies были бы пропущены.
- **Индекс поиска** пересобирается сам: `prebuild` вызывает `build:search` перед
  `next build`.
- **Переменные окружения** задаются в панели Amvera; как минимум
  `NEXT_PUBLIC_SITE_URL` с фактическим адресом приложения.
- **Не статический хостинг.** Приложению нужен Node-процесс: страницы персон
  статические, но `/katalog/` рендерится по фильтрам из строки запроса,
  а формы и генерация PDF-досье живут в обработчиках маршрутов.
